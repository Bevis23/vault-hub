# 多库架构设计思考

> 这是 README 里「为什么用多库架构」那一节的**完整版**。
> 如果你已经在用多库，这篇可以跳过 —— 它是写给还在犹豫的人，以及想把这个选择讲清楚的人。

---

## 一、先说结论

很多入门教程建议「所有笔记放一个库」。但在真实的多项目工作里，
**多库不是无奈的妥协，而是主动的架构选择** ——
它换来的隔离性（查询、同步、性能、隐私、交付）是单库靠文件夹 + 过滤规则很难等价实现的。

代价只有一个：**Obsidian 原生只看得见当前库**。
而**这个代价，正是 Vault Hub 要消灭的**。

---

## 二、多库带来的 11 种隔离

### 1. 查询 / 索引隔离

Dataview、全局搜索、标签面板、任务查询互不串数据。
A 项目的查询不会混入 B 项目的笔记，避免结果污染。

单库实现同等隔离需要大量复杂的过滤规则，而且要长期维护 ——
规则一多，就变成「为了隔离而写规则，最后规则本身成了负担」。

### 2. 同步与发布策略独立

不同库可以独立配置同步方案：云同步、Git 版本管理、博客发布。

合并为单库会让同步忽略规则、发布筛选变得极其复杂，极易泄露隐私内容 ——
「我只想发布技术笔记，别把日记同步上去」这种需求，单库里只能靠一堆 `.gitignore` 式的排除规则硬凑。

### 3. 性能隔离

归档项目库无需常驻索引，仅当前活跃库完整加载。
其他库只在需要时扫描，避免超大库索引膨胀，提升启动与查询速度。

### 4. 心理归档隔离

项目结束直接封存**整个知识库**。
相比单库内的文件夹归档，边界感更强、体系更干净 ——
「这个项目结束了」这件事，在文件系统上就是一个事实，不是一个命名约定。

### 5. 插件、主题、快捷键独立配置

每个仓库可拥有独立插件集、主题、快捷键、面板布局：

- 开发库：开启大量 Dataview、代码类插件
- 文献库：精简插件，保持轻量化
- 私密库：禁用第三方社区插件，降低安全风险

单库只能加载一套全集插件，无用插件常驻，易冲突、拖慢启动。

### 6. 安全与隐私边界隔离

合同、财务、账号等敏感资料单独隔离；
对接 AI 时可以限制 AI 仅访问素材库，私密库完全隔离，规避隐私泄露。

### 7. 插件 / 脚本试验场隔离

独立测试库用于尝试插件、CSS 片段、脚本模板。
即使折腾损坏元数据，也不会污染正式知识库。

### 8. 原创内容与外部素材隔离

网页剪藏、文献摘抄等外部素材，与个人原创思考分库存放，
方便版权梳理与知识萃取，保持原创库干净精简。

### 9. 协作交付边界隔离

分享给客户、同事时，仅交付目标项目库，
不需要附带全部个人笔记与其他项目资料，减少泄密风险。

### 10. 大附件资产隔离

PDF、录音、图片、视频等大容量媒体单独存放素材库，
避免主笔记库体积膨胀、索引变慢，保持主库轻量化。

### 11. 上下文专注隔离

工作时仅激活当前项目库，其他项目的待办、标签不会干扰当前视图，减少认知干扰。
单库哪怕用文件夹分类，任务看板仍会加载全部项目内容。

## 三、代价（以及为什么值得修，而不是绕开）

| 代价 | 说明 |
| --- | --- |
| **反复切窗口** | 原生没有跨库视图，看一眼别的库就要切换并重新加载 |
| **插件按库安装** | 切到没装插件的库，那套工具就消失了 |
| **库容易「被遗忘」** | 没有统一入口，归档库里躺着什么根本想不起来 |
| **跨库不可链接** | Obsidian 原生 `[[双链]]` 无法跨库（底层限制，插件无法伪造） |

前三条是**工程问题**，能修 —— 这正是 Vault Hub 在做的事。
最后一条是**底层限制**，我们选择不去伪造它（见下）。

---

## 四、工作台的取舍原则

保留多库的全部优势，消灭可修的代价。**但不为了消灭代价而破坏多库本身**：

| 做法 | 态度 | 理由 |
| --- | --- | --- |
| 合并库 | 🚫 永远不做 | 不可逆；中途失败就是两个半残的库，等于把上面 11 条优势一次性还回去 |
| 代做同步 / 备份 / 云冲突解决 | 🚫 永远不做 | 越界；本地插件无法知道另一台设备正在改什么，插手只会制造冲突 |
| 跨库双链 `[[Vault::Note]]` | 🚫 不做 | 非原生语法，卸载插件后退化成死链 —— **拿笔记的可移植性换一时方便，不值** |
| 跨库移动文件 | 🚫 不做 | 必然断链；用「跨库复制」替代（原件不动） |
| 统一视图 / 跨库浏览 / 切库自动化 | ✅ 做 | 只读优先，不破坏任何一方的结构 |

> 一句话：**工作台不碰你的库，只是让你看得见所有库。**

⛔ 红线（永远不做）：自动合并库、代用户同步 / 备份、跨库 `[[Vault::Note]]` 双链、跨库移动文件。

---

## 五、什么情况下**不该**用多库

诚实地说，多库不是万能的。出现下面这些情况时，单库往往更合适：

- 内容之间需要**大量互相引用**（比如知识网络型笔记，而不是项目型笔记）
- 需要**统一的全局搜索**，且不能接受插件式的检索
- 经常**在不同主题之间搬运**内容
- 主要靠**移动端**记笔记（本插件仅桌面端）

一个简单的判断标准：

> 如果你的笔记是**「按项目/领域切得开」**的 —— 多库合适；
> 如果是**「一张互相引用的网」** —— 单库更省心。
